## Release policy

### Supported Python versions

- **Minimum**: CPython 3.11 (per `pyproject.toml` `requires-python = ">=3.11"` and `pyo3/abi3-py311`).
- **Tested/supported**: 3.11, 3.12, 3.13, 3.14 (classifiers in `pyproject.toml`; CI builds and smoke-installs all four).
- **abi3 contract**: wheels are built once with the abi3 minimum (3.11) and install on all CPython 3.11+ interpreters. No per-version wheel is required; the smoke-install matrix proves the abi3 claim per minor version.
- **CPython only**: wheels target CPython (PyPy/GraalPy not supported in v0.1).

### Supported PostgreSQL versions

- **Production-readiness target**: PostgreSQL 16 (CI `security-gate-wheel` uses `postgres:16`).
- **Best-effort**: PostgreSQL 13+ (asyncpg supports 13+). PostgreSQL < 13 is not tested.
- **Other backends** (MySQL, SQLite, MSSQL): shipped extras are best-effort thin parity (§2.6, ProductManager resolution A). Not release gates.

### Upgrade / deprecation policy

- **Alpha (0.x)**: no semver/stability contract (§5a, ProductManager resolution A). Breaking changes may land in any 0.x release without deprecation or advance notice. The IR version has already moved.
- **After 1.0**: removing or breaking a documented public Python API requires a deprecation window of at least one minor release and 90 days, whichever is longer, recorded in `CHANGELOG.md` and `README.md`.
- **IR version**: internal PyO3 contract, not user-facing. After 1.0, an IR major bump is a Ferrum major-version event.
- **Generated SQL text**: never a compatibility surface. May change for correctness or performance without notice. Consumers must not parse SQL.

### Security reporting

- **Private reporting**: report security vulnerabilities via GitHub Security Advisories (the "Report a vulnerability" button on the repo's Security tab) — not via public issues.
- **Response SLA**: acknowledge within 5 business days. Target fix release within 30 days for High/Critical.
- **Security advisories**: published as GitHub Security Advisories with a CVE assignment request when applicable.
- **Supported versions for security fixes**: only the latest 0.x release receives security fixes (alpha policy). After 1.0, the latest minor of the current major receives fixes.

### Release candidates (RCs)

- **RC trigger**: optional, at the maintainer's discretion for major/minor releases. RCs are tagged `vX.Y.ZrcN` and published to TestPyPI (not PyPI).
- **RC workflow**: not in the current `release.yml` (which publishes to PyPI on `v*` tag push). A future RC workflow would add a `v*rc*` tag trigger and target TestPyPI with `pypa/gh-action-pypi-publish@release/v1` (test repository URL).
- **RC stability**: RCs are for testing only; not production-supported.

### Rollback / yank procedure

- **Yank**: PyPI yank (not delete) via the PyPI web UI or `twine` — removes the file from the simple index but keeps the record for installed dependents. Yank is the correct action for a broken release; deletion is reserved for legal/PII emergencies and requires PyPI admin.
- **Rollback to prior version**: pin consumers to the last known-good version (`ferrum-orm==X.Y.Z`). The abi3 wheel for the prior version remains on PyPI.
- **Revert migration code**: if a release ships a migration regression, consumers pin the prior Ferrum version and revert the migration ledger entry (Django-style `ferrum revert`). The ledger is per-database; no global rollback.
- **Emergency**: cut a patch release (`vX.Y.Z+1`) with the fix. Do not re-push the broken tag (force-push tags is disabled).

### Changelog ordering

- **Format**: Keep a Changelog (`https://keepachangelog.com/en/1.1.0/`) sections: Added, Changed, Deprecated, Removed, Fixed, Security.
- **Entry order within a section**: most recent first (reverse-chronological).
- **Version headers**: `## [X.Y.Z] — YYYY-MM-DD` (Unreleased section at top for pending changes).
- **Security entries**: go in the `Security` section, not `Fixed`, even if the fix is a bug.
- **Breaking changes**: tagged with a `BREAKING:` prefix in the entry and referenced in the 0.x→next migration notes.
- **Release ordering**: releases appear in reverse-chronological order in `CHANGELOG.md`. The `release.yml` workflow does NOT auto-generate changelog entries — the maintainer edits `CHANGELOG.md` before tagging.

### Supply chain security

- **cargo audit**: runs in the `cargo-audit` release job on every `v*` tag push. Denies warnings. New advisories block the release.
- **Dependency review**: GitHub's `dependency-review-action` runs on PRs (not in `release.yml`). Release-time dependency state is captured by `cargo audit` and `pip-audit` (dev extra).
- **SBOM / provenance**: `actions/attest-build-provenance@v1` generates signed build provenance attestations for wheel and sdist artifacts, verifiable via `gh attestation verify` or Sigstore.
- **PyPI attestations**: `pypa/gh-action-pypi-publish@release/v1` with `attestations: true` generates PyPI sigstore attestations (OIDC-backed, no long-lived key).
- **License checks**: `pyproject.toml` declares `license = { text = "Apache-2.0" }` and `include = ["LICENSE"]` in maturin config. The sdist carries `LICENSE`. A dedicated license-scan job is not in `release.yml` (document this gap for a future task).
- **Secret scanning**: GitHub's built-in secret scanning (push protection) is enabled at the repo level. `release.yml` does not run a dedicated secret scanner (e.g., trufflehog/gitleaks); document this as a follow-up.
- **Artifact signing**: OIDC trusted publishing (no long-lived PyPI token). Sigstore attestations via `pypa/gh-action-pypi-publish@release/v1`. No PGP/GPG wheel signing (not standard for PyPI).
