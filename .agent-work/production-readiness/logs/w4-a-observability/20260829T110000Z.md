## Findings fixed

### #1 (HIGH) — metric handlers cross-contaminate by event type
**Root cause:** `enable_metrics()` registered all 10 metric handlers via
`register_hook("*", fn)`. Only `_on_pool_event` guarded internally. Every
`query_success` dispatch inflated transaction/migration/retry/timeout counters,
and every `pool_acquire` inflated query counters.

**Fix:** Changed `enable_metrics()` to register each handler for its specific
event(s) instead of `"*"` (`observability.py:265-280`). `_on_pool_event` stays on
`"*"` because it already guards internally via `metric_map`. `_on_migration_event`
is registered for both `migration_start` and `migration_end`. This fixes
cross-contamination in both directions (query↔pool, query↔transaction, etc.).

**Regression tests added** (`test_observability.py`):
- `test_query_dispatch_does_not_inflate_non_query_metrics`
- `test_pool_dispatch_does_not_inflate_query_metrics`
- `test_transaction_dispatch_does_not_inflate_query_metrics`

### #2 (MEDIUM) — no behavioral test for span-around-query
**Root cause:** Only the OTel import-error path was tested. No test exercised the
`query_start → query_success/failure` span lifecycle or the orphan-success
fallback.

**Fix:** Added `TestOTelSpanLifecycle` with 3 behavioral tests using a fake
in-memory OTel tracer (`_FakeTracer`/`_FakeSpan`) injected via `sys.modules`
monkeypatch. The real `opentelemetry-sdk` is not installed (only the `otel` extra
`opentelemetry-api` exists, and it's not in `dev` deps); `pyproject.toml` is
outside owned paths so a mock-based approach was used (explicitly allowed by the
finding: "mock or real OTel tracer").

Tests:
- `test_query_success_creates_span_with_duration` — exactly one span named
  `ferrum.query`, `span.ended is True`, `duration_ms` attribute present,
  `_active_query_span` cleared afterward.
- `test_query_failure_creates_span` — same assertions for the failure path.
- `test_orphan_success_creates_fallback_span` — `query_success` without
  `query_start` creates a fallback span that is ended.

### #3 (LOW) — duplicate HELP/TYPE in Prometheus exposition
**Root cause:** `render_prometheus()` emitted `# HELP`/`# TYPE` once per metric
key; multi-label-set families got duplicated header lines.

**Fix:** Group `_METRICS` keys by family, emit HELP/TYPE once per family, then all
samples for that family (`observability.py:540-554`).

**Regression test:** `test_render_prometheus_help_type_once_per_family` —
dispatches 2 query_success events with different operations, asserts
`# HELP`/`# TYPE` appear exactly once for `ferrum_query_count`.

### #4 (LOW) — pool "gauge" metrics accumulate instead of setting
**Root cause:** `_on_pool_event` used `record_metric` (`+=`) for pool snapshot
fields declared as `gauge`. `pool_size` 10 then 8 → 18.0, not 8.0.

**Fix:** Added `set_gauge(name, value, labels=)` (`observability.py:72-78`) that
assigns (`=`) instead of accumulating (`+=`). Changed `_on_pool_event` gauge loop
to call `set_gauge` for the 4 snapshot fields (`observability.py:204-211`).

**Regression tests:**
- `test_pool_gauge_sets_not_accumulates` — two pool_acquire events, asserts
  `ferrum.pool.size == 8.0` (last value, not 18.0).
- `test_set_gauge_overwrites_not_accumulates` — direct `set_gauge` unit test.
