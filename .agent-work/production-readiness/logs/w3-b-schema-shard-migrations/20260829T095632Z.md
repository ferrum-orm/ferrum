## Execute

### Decisions

1. **Per-target advisory locks**: Derived a stable signed-int32 key from a fixed W3-B namespace (`b"ferrum.migrations.coordinator"`) + per-target hash. Uses `pg_advisory_xact_lock(int4, int4)` — same pattern as W1-C but with a distinct namespace key1 so the coordinator does not collide with a concurrently-running W1-C `apply()`. The `_to_int32` helper masks unsigned hash bytes to signed int32 (asyncpg rejects unsigned values > 2**31-1 for int4 parameters).

2. **Ledger digest**: The coordinator records the file-content digest (`ledger.compute_digest(name, content)`) — NOT the plan-JSON digest. This matches `MigrationGraph.status()` (W3-A) which compares the stored digest against the file-content digest. Using `apply()` directly would record the plan-JSON digest and break the graph's checksum comparison.

3. **Apply path**: Mirrored the CLI's `_apply_migration_postgres` pattern (W1-C): pre-tx non-transactional ops in autocommit, then a pinned-connection transaction with advisory lock + ledger check + tx ops + atomic ledger write, then post-tx non-transactional ops in autocommit. This reuses `_split_ops_by_phase`, `_op_to_sql`, `_is_op_destructive` from `orchestrator.py` (import only — no modification).

4. **Schema-tenant constraint**: When a target has a schema set, the apply is wrapped in `schema_transaction` (W1-F). Non-transactional ops (CREATE EXTENSION, CREATE INDEX CONCURRENTLY) are rejected in the schema path because they cannot run inside a `schema_transaction`. The caller must apply such migrations without schema selection or split them.

5. **Idempotent reruns**: Two levels of idempotency: (a) `MigrationGraph.upgrade_plan()` filters out already-applied migrations from the per-target ledger; (b) the W1-C replay guard (`is_applied_on_conn`) inside the transaction catches concurrent races. Migrations filtered by `upgrade_plan()` are tracked as "skipped" in the coordinator result.

6. **Fail-fast vs continue**: `fail_fast` (default) raises on the first target failure after recording it; `continue` collects all failures and returns a full result. Canary failures halt the rollout regardless of policy.

7. **Progress hooks**: Sync or async; exceptions from hooks are swallowed (observability must not break the rollout) but logged to stderr.

8. **`routing.py` extension**: Added `ConnectionRegistry.items()` returning `(name, Connection)` pairs — purely additive, no behavior change.
