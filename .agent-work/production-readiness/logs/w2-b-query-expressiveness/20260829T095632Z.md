## Execute

### What was implemented

1. **expressions.py — Reusable expression classes** (compiles through existing IR v4):
   - `F` class: Typed field reference expression for use in filters, aggregates, order_by, group_by
   - `Star` class: Marker for `COUNT(*)` explicit intent
   - `Combinable` base class: Base for composable expression types
   - `resolve_field_name` helper: Normalizes `str | F` to `str`, rejects other types

2. **queryset.py — Safety guards and F/Star integration**:
   - `_MAX_SELECT_RELATED_DEPTH = 5`: Maximum relations per `select_related()` call
   - `_MAX_TOTAL_JOINS = 12`: Maximum total JOINs per compiled query (select_related + filter joins)
   - `_DEFAULT_UNBOUNDED_LIMIT = 0`: Configurable unbounded-query guard (disabled by default)
   - `select_related()`: Added duplicate relation detection (cycle prevention) and depth limit enforcement
   - `_build_ir()`: Added total JOIN count check after building all joins
   - `Aggregate` factory methods (`count`, `sum`, `avg`, `min`, `max`): Now accept `F` and `Star` expressions
   - `group_by()`, `date_trunc()`, `order_by()`: Now accept `F` expressions alongside plain strings
   - All existing W1-A/W1-B features preserved (filter(None), cast matrix, write-scope guards, select_for_update, is_write)

3. **emit.rs — Pre-existing build fix** (not a new feature):
   - Added `FieldType::Citext => "citext"`, `FieldType::Inet => "inet"`, `FieldType::Domain => "text"` to `postgres_value_cast` match
   - These `FieldType` variants were added by W2-A (parallel workstream) but the emitter match wasn't updated, causing a build failure
   - Domain uses "text" as a safe fallback; W2-A should pass the domain name through IR for exact casts

4. **Tests**:

   - Integration tests: 5 tests against live PostgreSQL covering grouped filtered aggregates with F expressions, distinct, exists/not-exists patterns, select_related guard, F in order_by

### What was NOT implemented (blockers — require new IR nodes)

Per the constraint "Do NOT bump IR version or introduce new IR nodes without escalating (ChiefArchitect gate)", the following acceptance criteria require new IR nodes and are recorded as blockers:

1. **Multi-hop relation lookups** — `JoinSpec` needs a `from_alias: Option<String>` field to chain from a previous join's remote table. Current `JoinSpec.local_field` references the base model only.
2. **WHERE EXISTS/NOT EXISTS subqueries** — The existing `exists` flag is for `SELECT EXISTS(subquery)`, not `WHERE EXISTS(SELECT ...)`. Needs a new `Predicate` variant.
3. **Scalar subqueries** — Needs a new expression type in the IR.
4. **Conditional expressions (CASE WHEN)** — Needs new IR nodes for conditional logic.
5. **Database functions** — Needs a new expression type for allowlisted function calls.
6. **Window functions** — Needs new IR nodes for OVER/PARTITION BY.
7. **CTEs (WITH clauses)** — Needs new IR nodes for common table expressions.
8. **UNION/INTERSECT/EXCEPT** — Needs new IR nodes for set operations.

These are escalated to the coordinator for ChiefArchitect review. The Python-side API surface for these features should be designed alongside the IR changes.
