   branch emits only `ALTER TABLE ... FORCE ROW LEVEL SECURITY` when
   `EnableRLS(table, force=True)` is applied and never emits the paired
   `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. Postgres semantics: with
   `relrowsecurity` left `false`, every RLS policy on the table is a silent
   no-op regardless of which role connects — not merely the narrower
   "owner bypasses RLS" gap that `FORCE` alone is meant to close. Cited real
   Ticket Analyzer consumer code that documents exactly the ENABLE+FORCE
   combination a Ferrum-migrated equivalent must reproduce:
   `migrations/0018-force-rls.sql:3-20` (a defense-in-depth migration adding
   `FORCE ROW LEVEL SECURITY` on top of `ENABLE ROW LEVEL SECURITY` from an
   earlier migration, explicitly to close the table-owner RLS-bypass gap).
   Added a new, isolated `pytest.mark.xfail(strict=True)` regression test,
   `test_force_rls_without_enable_rls_grants_no_isolation_defect`, that
   applies **only** `EnableRLS(table, force=True)` (no prior plain
   `EnableRLS`) plus a `team_isolation` policy, then asserts the
   correct/fixed behavior (zero rows visible with no `app.team_id` GUC
   bound) — which currently fails (rows from both teams leak through),
   proving the defect with `strict=True` so an accidental fix would flip the
   test to an unexpected-pass failure, forcing conscious removal of the
   `xfail` marker.
3. **Fixture isolation fix.** The RLS workaround (two `EnableRLS` ops: plain
