## Adversarial checks

### Could the docstring fix hide a real bug?

The per-attempt deadline behavior is safe: each attempt's
`asyncio.timeout(deadline)` wraps only that attempt's transaction. If
attempt 1 takes the full budget and fails with a retriable SQLSTATE,
attempt 2 gets a fresh full budget. This is more lenient than "all
attempts combined" but is safe — the alternative (tracking remaining
time) would be more restrictive. The §5a contract says "honor
cancellation/deadline" without specifying total vs. per-attempt; the
implementation honors it per-attempt, which the docstring now reflects
honestly. No consumer-backed requirement for total-budget tracking was
cited. This is the verifier's Option (b) from the prior run.

### Could the dead-code removal change retry behavior?

`_exception_category` is called only by `RetryPolicy.should_retry`,
which checks `category in self.on`. Since `RetryPolicy.__post_init__`
(line 100-107) rejects any `on` set containing `"connection"` with
`ValueError("Unknown retry categories...")`, no constructed
`RetryPolicy` can have `"connection"` in `on`. Therefore
`should_retry` could never return `True` for a connection-class
exception, regardless of whether `_exception_category` returned
`"connection"` or `None`. The removal is behavior-preserving for all
valid `RetryPolicy` instances.
