### C1 — Lifespan hardening (independent source inspection)

`python/ferrum/connection.py:105` defines `_EventLifecycleGuard` with an
`asyncio.Event`-based `wait_drained(timeout=...)` (lines 133-142).
`Connection.close()` (line 322) calls
`await self._lifecycle.wait_drained(timeout=self._runtime.drain_timeout)`.
`ferrum.connect()` (line 1043) accepts `drain_timeout: float = 30.0`
(line 1060) and threads it into `Connection(...)`. `ferrum_lifespan`
forwards `drain_timeout` (and every other W1-E knob) into `connect(...)`.
Verified by reading `python/ferrum/connection.py:1043-1110` and the diff
of `python/ferrum/contrib/fastapi.py`.

The lifespan yields a single `Connection` (which IS the pool); the
dependency pulls from `app.state.ferrum_conn`. One pool per process is
enforced by design — there is no per-request `connect()` call. The
concurrent-requests integration test (5 simultaneous POSTs against a
pool with `max_size=5`) confirms requests do not serialize.

### C2 — Transaction-scoped dependencies (independent source inspection)

`get_ferrum_transaction` (diff lines, `fastapi.py`) acquires
`conn = request.app.state.ferrum_conn`, validates it is a `Connection`,
then `async with conn.transaction() as tx: yield tx`. The
`async with` guarantees commit-on-clean-exit and rollback-on-exception
(inherited from `Transaction.__aexit__`). The unit tests
`test_get_ferrum_transaction_yields_transaction_and_commits_on_clean_exit`
and `test_get_ferrum_transaction_rolls_back_on_exception` exercise both
paths with mocked `Transaction.__aexit__`. The integration tests
`test_fastapi_get_ferrum_transaction_commits_on_clean_exit` and
`..._rolls_back_on_exception` exercise both paths against live
PostgreSQL (the rollback test asserts no row survives a unique
violation).

### C3 — Error translation / redaction (independent adversarial test)

Ran an independent adversarial probe directly against
`ferrum_exception_handler` with crafted exceptions whose `str(exc)`
contains DSN, DETAIL, email, password, and row data:

```python
# IntegrityError with sensitive DETAIL + DSN in str(exc)
exc = FerrumIntegrityError(
    "Duplicate key. DETAIL (key)=(user@example.com). "
    "DSN=postgresql://u:pw@host:5432/db",
    constraint="uq", sqlstate="23505", category="unique_violation",
    model="User", operation="insert",
)
resp = ferrum_exception_handler(None, exc)
body = json.loads(resp.body)
# body == {'error': {'code': 'FERR-D201', 'category': 'unique_violation',
#   'sqlstate': '23505', 'constraint': 'uq', 'model': 'User',
#   'operation': 'insert'}}
# All of 'user@example.com', 'password', 'host', 'DETAIL', 'Duplicate key',
# 'postgresql://' absent from str(body). PASS.
```

Also exercised `FerrumConnectionError` carrying a DSN in the message
and `FerrumDatabaseError` carrying row data — both translated to safe
payloads, no leakage. Base `FerrumError()` returns
`{'error': {'code': 'FERR-0000'}}` only.

The integration test
`test_fastapi_get_ferrum_transaction_rolls_back_on_exception` confirms
the 409 response carries `code`/`sqlstate` but not the email value
(`"dup@test" not in body_text`).

Source: `_sanitize_ferrum_error_payload` (diff) builds a payload with
only `code`/`category`/`sqlstate`/`constraint`/`model`/`operation`,
omitting `None` fields. It never reads `str(exc)`. This matches the
ratified §5a safe-error-field set.
