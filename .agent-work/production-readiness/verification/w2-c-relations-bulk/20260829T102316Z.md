## Adversarial checks

### Defect 1 (changes_required): False composite-PK claim in `_ReverseRelationDescriptor` docstring

`python/ferrum/relations.py:269-272` docstring states:

> "Composite primary keys are honored: the unbound QuerySet is filtered by all PK columns when the parent model uses a composite PK."

But the code at `relations.py:292` is:

```python
pk_val = getattr(obj, "id", None)
return QuerySet(related).filter(**{self._meta.fk_column: pk_val})
```

The code hardcodes `"id"` and filters by a single FK column — it does NOT honor composite PKs and does NOT filter by "all PK columns". The executor's log acknowledges this in "Risks and follow-up" ("does not use composite PK fields … no consumer currently needs this"), but the docstring was not corrected to match the code. This is a documentation-accuracy defect that violates AGENTS.md §8 (DoD: errors/docs must be accurate and actionable).

**Fix**: Either correct the docstring to remove the false composite-PK claim, or implement composite-PK support using `_instance_pk_values` (currently dead code — see Defect 3).

### Defect 2 (changes_required): Misleading M2M ordering docstring

`python/ferrum/relations.py:623` (`_prefetch_m2m`) and `relations.py:455-466` (`prefetch_related_objects`) claim "Results are ordered by the target model's PK for deterministic output."

The Phase 2 target fetch (line 674-678) does `ORDER BY {target_pk_ident}`, but the final per-parent M2M list is built at line 690:

```python
[by_id[tid] for tid in links.get(pid, []) if tid in by_id]
```

This iterates `links[pid]` (through-table link order from Phase 1), NOT `by_id` (target PK order). Phase 1 SQL (line 650-653) has NO `ORDER BY`, so the through-table link order is non-deterministic. The per-parent M2M list order therefore follows the through-table link order, not the target PK order. The "deterministic output" claim is true for reverse FK (line 586 `ORDER BY pk_column` orders `grouped[pid]`), but FALSE for M2M.

No test asserts M2M per-parent ordering — `test_reverse_fk_prefetch_orders_by_pk` only covers reverse FK.

**Fix**: Either correct the docstring to scope the ordering claim to reverse FK (or qualify "target rows are fetched with ORDER BY PK; per-parent list order follows through-table link order"), OR add `ORDER BY owner_ident, target_ident` to Phase 1 so `links[pid]` is ordered by target PK.

### Defect 3 (changes_required): Dead code — YAGNI violation

`python/ferrum/relations.py:167-174` defines two helpers:

```python
def _model_pk_fields(metadata: ModelMetadata) -> list[tuple[str, str]]: ...
def _instance_pk_values(obj: Model, metadata: ModelMetadata) -> list[Any]: ...
```

`grep -rn "_instance_pk_values\|_model_pk_fields" python/ferrum/ tests/` → only the definitions; zero call sites in source or tests. These helpers are dead code. They appear to have been added to support composite-PK in the reverse descriptor (Defect 1) but were never wired in. AGENTS.md §7: "No speculative complexity (YAGNI). Implement only consumer-backed plan requirements."

**Fix**: Remove both helpers (and the Defect 1 docstring fix removes the implication that they should be used).
