## Findings

### #1 — HIGH (correctness defect): metric handlers cross-contaminate by event type

`python/ferrum/observability.py:171-203`

`_on_transaction_start`, `_on_transaction_end`, `_on_migration_event`,
`_on_retry_attempt`, `_on_timeout_event` are registered via `register_hook("*", fn)`
in `enable_metrics()` (line 261-274) but **do not filter by `payload["event"]`**.
Only `_on_pool_event` (line 178: `event = str(payload.get("event", ""))`) and the
query/hydration handlers guard on event type.

Consequence (reproduced above): dispatching `query_success` twice increments
`ferrum.transaction.count`, `ferrum.migration.count`, `ferrum.retry.count`, and
`ferrum.timeout.count` — each by 2.0. The "low-cardinality metrics from Tier-A-safe
fields" acceptance criterion is satisfied in cardinality but the **values are
wrong**: every query dispatch inflates every non-query counter.

The existing unit tests (`test_transaction_start_end_metrics`,
`test_migration_event_metrics`, `test_retry_attempt_metric`,
`test_timeout_event_metric`) only assert the relevant metric *exists* after
dispatching the matching event; they never assert that *other* metrics do NOT
increment, so the cross-contamination is uncaught.

**Required correction:**
- Add an event-type guard at the top of each of the five handlers, e.g.
  `if str(payload.get("event", "")) != "transaction_start": return`.
- Add regression tests in `test_observability.py` that dispatch a `query_success`
  and assert `ferrum.transaction.count`, `ferrum.migration.count`,
  `ferrum.retry.count`, `ferrum.timeout.count` are all absent (or zero).

### #2 — MEDIUM (DoD test-coverage gap): no behavioral test for span-around-query

`tests/python/unit/test_observability.py`, `tests/python/integration/test_observability_integration.py`

Acceptance criterion #1 ("One span around actual query execution") is the
headline of this task and is verified by the independent verifier only via
**source inspection** (verification report §1). No unit or integration test
exercises the OTel span lifecycle:
- `query_start` opens a span and stores it in `_active_query_span`;
- `query_success`/`query_failure` retrieves, attributes, and `span.end()`s it;
- the contextvar is cleared after each query;
- the orphan-success fallback span (observability.py:378-382) fires when
  success arrives without a matching start.

The only OTel test present is `test_enable_opentelemetry_requires_dependency`
(test_observability.py:474-480), which covers the import-error path only.
AGENTS.md §2.7 ("No ORM feature ships without tests") and §8 DoD require
behavioral coverage for new behavior.

**Required correction:**
- Add a unit test using `opentelemetry-sdk`'s `InMemorySpanExporter` (already a
  dev extra) that enables OTel, dispatches `query_start` → `query_success`,
  and asserts: exactly one span named `ferrum.query`, `span.end()` was called,
  `duration_ms` attribute present, `_active_query_span` cleared afterward.
- Add a parallel test for `query_start` → `query_failure`.
- Add a test for the orphan-success fallback (success without start) asserting
  a fallback span is created and ended.

### #3 — LOW (correctness, test/dev helper): duplicate HELP/TYPE in Prometheus exposition

`python/ferrum/observability.py:530-542`

`render_prometheus()` iterates `_METRICS` per key and emits `# HELP` / `# TYPE`
for each key. When a metric family has multiple label-sets, HELP/TYPE are
emitted once per key, producing duplicate lines per family. Reproduced:
`ferrum_query_count` family emits `# HELP`/`# TYPE` 4 times in the output above.

Prometheus text exposition format requires HELP and TYPE to appear **exactly
once per metric family** before the samples. A strict Prometheus parser will
reject or warn on duplicate HELP/TYPE lines.

`test_render_prometheus_emits_help_type` only dispatches one query (one
label-set), so it does not catch this.

**Required correction:**
- Group `_METRICS` keys by family; emit HELP/TYPE once per family, then all
  samples for that family.
- Add a test that dispatches ≥2 events producing different label-sets for the
  same family and asserts `# HELP`/`# TYPE` appear exactly once for that family.

### #4 — LOW (semantics): pool "gauge" metrics accumulate instead of setting

`python/ferrum/observability.py:196-203`, `record_metric` (line 48-54)

`_on_pool_event` records pool snapshot fields (`pool_size`, `pool_idle`,
`pool_acquired_count`, `pool_waiters`) via `record_metric`, which does
`_METRICS[key] += value`. These are declared `gauge` in `render_prometheus`
`type_map` (line 516-519) but behave as counters: two `pool_acquire` events
with `pool_size` 10 then 8 produce `ferrum.pool.size = 18.0`, not `8.0`.

Reproduced in the evidence output above (`ferrum_pool_size 18.0`).

The in-process registry is documented as a test/dev helper, so severity is LOW,
but the `gauge` TYPE declaration is misleading and any consumer of
`render_prometheus()` will read wrong gauge values for repeated pool events.

**Required correction (either):**
- Add a `set_gauge(name, value, labels)` path that assigns rather than
  accumulates, and use it for the four pool snapshot fields; or
- Drop the `gauge` TYPE for these four metrics and document them as counters
  of the last-observed snapshot (less useful but honest).

### #5 — INFO: dangling comment in OTel query span block

### #6 — INFO: transaction OTel span is zero-duration (pattern inconsistency)

`python/ferrum/observability.py:410-414`

`transaction_start` creates `with tracer.start_span("ferrum.transaction",
attributes=...): pass` — a zero-duration span — then emits a counter. This
revives the "zero-duration event span per dispatch" pattern the task explicitly
eliminated for queries. There is no `transaction_start`→`transaction_end` span
pairing analogous to the query span.

**Required correction (either):** pair `transaction_start`/`transaction_end`
into one span via a contextvar (analogous to `_active_query_span`), or drop the
span and emit only the counter (the counter is the useful signal). Leaving a
zero-duration `pass` span is the worst of both.
